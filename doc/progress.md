## 附录 C：配置模型统一方案

**状态: ✅ 已解决**

项目中存在两套配置模型（config.rs 持久化层 + 业务层），已通过 `From` trait 实现自动转换，并**删除业务层的 `Default` 实现**，确保默认值唯一来源。

| 转换实现 | Default 状态 |
|----------|-------------|
| `From<&HttpConfig> for HttpServerConfig` | ✅ 已删除 |
| `From<&TftpdConfig> for TftpServerConfig` | ✅ 已删除 |
| `From<&TftpcConfig> for TftpClientConfig` | ✅ 已删除 |
| `From<&ChatModuleConfig> for ChatConfig` | ✅ 已删除 |

**架构原则**：
1. 保留分层配置设计（良好的架构实践）
2. config.rs 负责持久化，业务层负责运行时
3. **业务层不再保留 Default 降级方案**，所有默认值以 config.rs 为准
4. 核心服务 `new()` 使用内部占位配置，`init()` 必须传入从 config.rs 转换的配置

详见 `doc/requirements-gap-analysis.md` 配置模型重复问题章节。

## 附录 D：TFTPC 端口配置分析

### 旧方案实现方式

根据 `doc/resources_bak/tftpc.PNG` 截图和需求文档分析：

#### 界面布局
旧版本 TFTPC 界面包含：
- **IP 输入框**: 服务器地址（如 `127.0.0.1`）
- **Opt. 输入框**: 选项字符串，格式为 `key=value;key=value;`
  - 示例: `timeout=200;retry=10;blksize=1468;`

#### 端口配置方式

**旧方案**：端口通过选项字符串配置

```
timeout=200;retry=10;blksize=1468;port=69;
```

- 端口不是独立的 UI 控件
- 端口作为选项字符串的一部分，通过解析 `opts_string` 获取
- 默认端口 69 在解析时作为 fallback

#### 当前实现状态

| 配置项 | 需求文档 | config.rs | 旧方案 | 当前 UI |
|--------|---------|-----------|--------|---------|
| server_addr | 必需 | ✅ server_addr | IP 输入框 | ✅ 有 |
| server_port | 需求文档定义 | ✅ server_port | 选项字符串中 | ❌ 无独立控件 |
| timeout | 必需 | ✅ timeout | 选项字符串 | ✅ 选项字符串 |
| maxretry | 必需 | ✅ maxretry | 选项字符串 | ✅ 选项字符串 |
| blksize | 必需 | ✅ blksize | 选项字符串 | ✅ 选项字符串 |

#### 分析结论

1. **需求文档要求 port 作为独立配置项**
   - `requirements.md` 2.5.2 节明确定义 port 为配置项
   - 默认值 69

2. **旧方案中端口通过选项字符串配置**
   - 端口不是独立控件
   - 用户可以在 Opt. 输入框中添加 `port=xxx`

3. **当前实现已支持端口配置**
   - `TftpcConfig` 有 `server_port` 字段
   - 默认值 69
   - 但 UI 上没有独立的端口输入框

#### 推荐方案

**保持当前实现**，原因：
1. `TftpcConfig.server_port` 已存在，默认值正确
2. 端口可以通过选项字符串配置（兼容旧方案）
3. 不需要添加独立端口输入框，保持界面简洁
4. 选项字符串格式：`timeout=200;retry=10;blksize=1468;` 已满足需求

如果需要明确端口配置，可以在选项字符串说明文档中添加端口配置示例。

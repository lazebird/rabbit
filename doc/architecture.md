# Rabbit 跨平台重写技术选型与架构设计

## 1. 项目背景与目标

### 1.1 当前问题

| 问题 | 描述 |
|------|------|
| 技术栈过时 | .NET Framework 4.7.2 仅支持 Windows |
| 无法跨平台 | 无法在 Linux/macOS 上运行 |
| 部署复杂 | 需要 ILMerge 合并 DLL，需预安装运行时 |
| 维护困难 | WinForms 设计器代码与逻辑耦合 |
| 体积过大 | 需预安装 .NET Framework |

### 1.2 重写目标

| 目标 | 要求 |
|------|------|
| 跨平台 | 支持 Windows、Linux 桌面 |
| 单文件 | 打包成单一可执行文件，无需预安装运行时 |
| 体积可控 | 控制在 10MB 以内（优选），上限 30MB |
| 性能优良 | 内存 < 50MB，启动 < 1秒，CPU 空闲时接近 0% |
| 简单易用 | 开箱即用，零配置启动 |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| 三层分离 | 功能层、数据层、界面层严格分离 |
| 优先复用 | 成熟功能/协议使用第三方库，避免重复造轮子 |
| 按需重写 | 导入代价高的直接重写，避免过度依赖 |
| 资源节约 | CPU/内存占用低，空闲时接近零开销 |

### 3.4 选型结论

#### 方案对比

| 方案 | 体积 | 核心功能覆盖 | 迁移成本 | 推荐度 |
|------|------|-------------|----------|--------|
| **保持 Slint + 补充功能** | 3-8 MB ✅ | 托盘/日历需额外实现 | 无 | ⭐⭐⭐⭐ |
| **迁移到 FLTK** | 1-3 MB ✅ | 全覆盖 ✅ | 中等（重写 UI） | ⭐⭐⭐⭐⭐ |
| 迁移到 Tauri | 80-100 MB ❌ | 全覆盖 ✅ | 高（Web 技术栈） | ⭐⭐ |
| 迁移到 Iced | 5-12 MB ✅ | IME 不支持 ❌ | 中等 | ⭐⭐ |

#### 推荐：迁移到 FLTK

**理由：**

1. **功能全覆盖**：系统托盘、日历选择器、右键菜单均为内置支持，无需额外集成
2. **体积最优**：1-3 MB，比 Slint 更小，完美符合 10MB 目标
3. **IME 完善**：中文输入支持最成熟，适合中文用户
4. **性能最优**：启动 50-150ms，内存 5-15MB
5. **Linux 单文件**：无外部依赖，完美符合部署要求

**权衡：**

- API 风格传统（回调式 vs 声明式）
- 布局系统较弱，需更多手动布局
- 需要重写 UI 代码

**迁移成本评估：**

| 项目 | 工作量 |
|------|--------|
| UI 重写 | 约 70% 代码改动 |
| 业务层复用 | 100% 复用（service/schema/adapter） |
| 学习曲线 | 中等（API 简单但风格不同） |

#### 备选：保持 Slint + 补充功能

如果迁移成本不可接受，可保持 Slint 并补充缺失功能：

| 缺失功能 | 解决方案 | 额外依赖 |
|----------|----------|----------|
| 系统托盘 | `tray-icon` crate | tray-icon, image |
| 日历选择器 | 自定义组件 或 系统对话框 | 无 或 zenity/kdialog |
| 右键菜单 | PopupWindow 自定义 | 无 |
| 任务栏进度 | 平台特定代码（windows-rs/dbus） | windows, dbus |

**额外工作量**：约 1-2 周

### 3.5 决策建议

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| **项目长期维护** | 迁移 FLTK | 功能完整，维护成本低 |
| **短期交付** | 保持 Slint | 无迁移风险，快速上线 |
| **极致体积要求** | FLTK | 1-3 MB 最小 |
| **中文用户体验优先** | FLTK | IME 支持最完善 |

## 4. 架构设计

### 4.1 三层分离架构

```
┌─────────────────────────────────────────┐
│           表现层 (Presentation)          │
│   View (UI组件) ← ViewModel (状态逻辑)   │
├─────────────────────────────────────────┤
│           业务层 (Business)              │
│   PingService / HttpService / ...       │
│   封装第三方库或自实现的业务逻辑           │
├─────────────────────────────────────────┤
│           数据层 (Data)                  │
│   Models (纯数据) + Repository (持久化)  │
├─────────────────────────────────────────┤
│        基础设施层 (Infrastructure)        │
│   WindowsPlatform / LinuxPlatform       │
└─────────────────────────────────────────┘
```

### 4.2 模块职责

| 层级 | 模块 | 职责 | 依赖 |
|------|------|------|------|
| 表现层 | View | UI 渲染、用户交互 | ViewModel |
| 表现层 | ViewModel | 状态管理、命令绑定 | Service |
| 业务层 | Service | 核心业务逻辑、协议处理 | Models, Platform |
| 数据层 | Models | 纯数据结构定义 | 无 |
| 数据层 | Repository | 配置/日志持久化 | Models |
| 基础设施层 | Platform | 平台相关功能抽象 | 无 |

### 4.3 项目结构

```
rabbit/
├── crates/
│   ├── app/              # 主程序入口 + UI 定义
│   ├── service/          # 业务服务层
│   ├── schema/           # 数据模型层
│   ├── adapter/          # 平台适配层
│   ├── rabbit-config/    # 配置持久化
│   └── rabbit-diag/      # 诊断日志
└── tests/
```

## 5. 第三方库选型

### 5.1 选型决策

| 模块 | Rust 方案 | Go 方案 | .NET 方案 | 决策依据 |
|------|----------|---------|-----------|---------|
| UI 框架 | slint / fltk | fyne | Avalonia | 跨平台成熟方案 |
| HTTP Server | axum | 内置 | EmbedIO | 轻量、无重依赖 |
| TFTP | async-tftp | 自实现 | Tftp.Net | 见 5.2 节 |
| Ping | surge-ping | go-ping | 内置 | 库成熟 |
| JSON | serde | 内置 | 内置 | 内置优先 |
| 配置 | config-rs | 内置 | 内置 | 需求简单 |
| 日志 | tracing | slog | 内置 | 需求简单 |
| 异步运行时 | tokio | goroutine | Task | 原生支持 |

### 5.2 TFTP 库选型

详细评估见 [TFTP 库选型评估](./tftp-evaluation.md)

**结论：推荐 async-tftp**

| 维度 | 说明 |
|------|------|
| 异步文件 I/O | ✅ 原生支持，网络与磁盘并行 |
| 缓存扩展 | ✅ 通过 Handler trait 可实现预读/写入缓存 |
| 窗口扩展 | ✅ RFC 7440 支持，提升吞吐量 |
| 功能 | 完整 TFTP 服务端 + 客户端 |
| 实现 | 纯 Rust，Apache-2.0 / MIT 双许可 |

### 5.3 核心依赖原则

- **优先内置**：使用语言/框架内置功能
- **轻量优先**：选择无重依赖的库
- **成熟优先**：选择社区活跃、文档完善的库
- **避免过度封装**：需求简单则自实现

### 5.4 配置模型设计

项目采用**双层配置模型**设计，通过 `From` trait 实现自动转换，确保默认值唯一来源。

#### 模型分层

| 层级 | 位置 | 职责 | 示例 |
|------|------|------|------|
| 持久化层 | `config.rs` | 配置文件序列化/反序列化，默认值定义 | `HttpConfig`, `TftpdConfig`, `ChatModuleConfig` |
| 业务层 | 各模块模型文件 | 运行时配置，业务逻辑使用 | `HttpServerConfig`, `TftpServerConfig`, `ChatConfig` |

#### 转换机制

```rust
// 业务层不提供 Default 实现，通过 From trait 从 config.rs 获取
impl From<&HttpConfig> for HttpServerConfig {
    fn from(config: &HttpConfig) -> Self { ... }
}

// 使用方式
let config: HttpServerConfig = (&app_config.modules.http).into();
```

#### 已实现转换的模块

| 模块 | From 实现 | Default 状态 |
|------|-----------|-------------|
| HTTP | `From<&HttpConfig> for HttpServerConfig` | 已删除 |
| TFTP Server | `From<&TftpdConfig> for TftpServerConfig` | 已删除 |
| TFTP Client | `From<&TftpcConfig> for TftpClientConfig` | 已删除 |
| Chat | `From<&ChatModuleConfig> for ChatConfig` | 已删除 |
| Scan | `From<&ScanConfig> for ScanRange` | 保留（无对应模型） |

#### 核心服务初始化模式

```rust
// new() 使用内部占位配置（不可用状态）
pub fn new() -> Self {
    Self {
        config: Arc::new(RwLock::new(Self::placeholder_config())),
        ...
    }
}

// init() 必须传入从 config.rs 转换的配置
pub async fn init(&mut self, config: BusinessConfig) -> Result<()> {
    *self.config.write().await = config;
    Ok(())
}
```

**设计原则**：
1. 默认值唯一来源为 `config.rs`，业务层不保留降级方案
2. 占位配置仅用于 `new()` 到 `init()` 之间的短暂过渡
3. 业务代码正常路径下只能通过 `From` trait 获取配置

## 6. 核心模块实现细节

### 6.1 HTTP 服务器模块

#### 架构

| 组件 | 技术 | 说明 |
|------|------|------|
| HTTP 框架 | axum | 基于 tower 的异步 HTTP 框架 |
| 静态文件 | tower-http ServeDir | 高效静态文件服务 |
| 访问日志 | 自定义 middleware | 记录请求/响应 |

#### 视频播放器实现

- **技术方案**: Video.js 7.1.0（与旧版 C# 实现兼容）
- **触发方式**: URL 查询参数 `videoplay=true`
- **支持格式**: MP4, WebM, OGG, AVI, MOV, WMV, FLV, MKV, M4V
- **MIME 映射**: 内置 HashMap 映射文件扩展名到 MIME 类型
- **实现方式**: 中间件拦截视频文件请求，返回包含 Video.js 播放器的 HTML 页面

```
请求: /videos/sample.mp4?videoplay=true
  ↓
中间件检测: 视频 MIME + video_play=true + 无 videoplay=false
  ↓
返回: Video.js 播放器 HTML 页面
  ↓
播放器加载: /videos/sample.mp4?videoplay=false (直接返回视频流)
```

#### 目录浏览实现

- **配置**: `auto_index` 控制开关
- **默认行为**: ServeDir `append_index_html_on_directories` 设置
- **优先级**: index.html > index.htm > 目录列表（启用时）

### WebView 方案评估结论

| 指标 | Tauri | Wails | Electron |
|------|-------|-------|----------|
| Linux 单文件可行性 | ⚠️ 需权衡 | ❌ 不支持 | ✅ 但体积大 |

### 迁移建议

**如果选择迁移到 FLTK：**

1. **复用层级**：
   - `service`: 100% 复用（业务逻辑与 UI 无关）
   - `schema`: 100% 复用（纯数据结构）
   - `adapter`: 100% 复用（平台适配层）

2. **重写层级**：
   - `app/ui/`: 需要用 FLTK API 重写所有 `.slint` 组件

3. **迁移策略**：
   - 先完成一个核心模块（如 Ping）的 FLTK 版本验证
   - 验证通过后逐步迁移其他模块
   - 保持三层架构不变，仅替换表现层

4. **风险**：
   - FLTK 编译依赖 CMake/C++（可通过预编译库缓解）
   - 布局系统较弱，需要更多手动调整

# Rabbit 跨平台重写技术选型与架构设计

## 1. 项目背景与目标

### 1.1 当前问题

| 问题 | 描述 |
|------|------|
| 技术栈过时 | .NET Framework 4.7.2 仅支持 Windows |
| 无法跨平台 | 无法在 Linux/macOS 上运行 |
| 部署复杂 | 需要 ILMerge 合并 DLL，需预安装运行时 |
| 维护困难 | WinForms 设计器代码与逻辑耦合 |
| 体积过大 | 需预安装 .NET Framework |

### 1.2 重写目标

| 目标 | 要求 |
|------|------|
| 跨平台 | 支持 Windows、Linux 桌面 |
| 单文件 | 打包成单一可执行文件，无需预安装运行时 |
| 体积可控 | 控制在 10MB 以内（优选），上限 30MB |
| 性能优良 | 内存 < 50MB，启动 < 1秒，CPU 空闲时接近 0% |
| 简单易用 | 开箱即用，零配置启动 |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| 三层分离 | 功能层、数据层、界面层严格分离 |
| 优先复用 | 成熟功能/协议使用第三方库，避免重复造轮子 |
| 按需重写 | 导入代价高的直接重写，避免过度依赖 |
| 资源节约 | CPU/内存占用低，空闲时接近零开销 |

## 3. 最终选型

### 3.1 Rust GUI 方案对比结论

| 方案 | 体积 | 优势 | 劣势 | Linux 单文件 | 推荐度 |
|------|------|------|------|-------------|--------|
| **FLTK** | 1-3 MB | 极致轻量、控件丰富、IME 完善 | API 老旧、布局弱 | ✅ 无依赖 | ⭐⭐⭐⭐ |
| **Slint** | 3-8 MB | 现代 API、布局强、无障碍完善 | DSL 学习成本 | ✅ 无依赖 | ⭐⭐⭐⭐⭐ |
| **Iced** | 5-12 MB | Elm 架构优雅、纯 Rust | 无障碍缺失、IME 不支持 | ✅ 无依赖 | ⭐⭐⭐ |
| **Tauri** | 3-10 MB / 80-100 MB | Web 技术、生态成熟 | Linux 打包两难 | ⚠️ 需依赖或体积大 | ⭐⭐⭐ |

### 3.2 推荐方案

**主推：Rust + Slint**

| 指标 | 数值 | 优势 |
|------|------|------|
| 二进制体积 | 3-8 MB | 比 .NET 小 4-10 倍 |
| 内存占用 | 10-20 MB | 比 .NET 低 3-5 倍 |
| 启动时间 | 100-300ms | 比 .NET 快 2-5 倍 |
| 运行时依赖 | 无 | 真正单文件部署 |

**选择理由：**
1. 体积性能优秀，仅次于 FLTK
2. 现代 API 设计，开发体验好
3. 布局系统完善，适合复杂 UI
4. 无障碍支持完善，符合现代标准
5. 纯 Rust 实现，编译依赖轻量

**备选：Rust + FLTK**

适用场景：
- 对体积有极致要求（1-3 MB）
- 需要丰富的内置控件
- 需要完善的 IME 支持（中文输入）
- 可接受传统 API 风格

**保守：Go + Fyne / .NET Avalonia**

适用场景：
- 追求开发效率
- 迁移成本敏感

### 3.3 方案对比总结

| 方案 | 体积 | 内存 | 启动 | 开发效率 | 推荐场景 |
|------|------|------|------|---------|---------|
| **Rust FLTK** | 最优 | 最优 | 最优 | 中 | 极致体积要求 |
| **Rust Slint** | 优 | 优 | 优 | 中 | 综合最优选择 |
| Go + Fyne | 中 | 良 | 良 | 高 | 开发效率优先 |
| .NET Avalonia | 差 | 差 | 中 | 最高 | 迁移成本优先 |

## 4. 架构设计

### 4.1 三层分离架构

```
┌─────────────────────────────────────────┐
│           表现层 (Presentation)          │
│   View (UI组件) ← ViewModel (状态逻辑)   │
├─────────────────────────────────────────┤
│           业务层 (Business)              │
│   PingService / HttpService / ...       │
│   封装第三方库或自实现的业务逻辑           │
├─────────────────────────────────────────┤
│           数据层 (Data)                  │
│   Models (纯数据) + Repository (持久化)  │
├─────────────────────────────────────────┤
│        基础设施层 (Infrastructure)        │
│   WindowsPlatform / LinuxPlatform       │
└─────────────────────────────────────────┘
```

### 4.2 模块职责

| 层级 | 模块 | 职责 | 依赖 |
|------|------|------|------|
| 表现层 | View | UI 渲染、用户交互 | ViewModel |
| 表现层 | ViewModel | 状态管理、命令绑定 | Service |
| 业务层 | Service | 核心业务逻辑、协议处理 | Models, Platform |
| 数据层 | Models | 纯数据结构定义 | 无 |
| 数据层 | Repository | 配置/日志持久化 | Models |
| 基础设施层 | Platform | 平台相关功能抽象 | 无 |

### 4.3 项目结构

```
rabbit/
├── crates/
│   ├── rabbit-app/       # 主程序入口 + UI 定义
│   ├── rabbit-core/      # 业务服务层
│   ├── rabbit-models/    # 数据模型层（无外部依赖）
│   └── rabbit-platform/  # 平台适配层
└── tests/
```

## 5. 第三方库选型

### 5.1 选型决策

| 模块 | Rust 方案 | Go 方案 | .NET 方案 | 决策依据 |
|------|----------|---------|-----------|---------|
| UI 框架 | slint / fltk | fyne | Avalonia | 跨平台成熟方案 |
| HTTP Server | axum | 内置 | EmbedIO | 轻量、无重依赖 |
| TFTP | async-tftp | 自实现 | Tftp.Net | 见 5.2 节 |
| Ping | surge-ping | go-ping | 内置 | 库成熟 |
| JSON | serde | 内置 | 内置 | 内置优先 |
| 配置 | config-rs | 内置 | 内置 | 需求简单 |
| 日志 | tracing | slog | 内置 | 需求简单 |
| 异步运行时 | tokio | goroutine | Task | 原生支持 |

### 5.2 TFTP 库选型

详细评估见 [TFTP 库选型评估](./tftp-evaluation.md)

**结论：推荐 async-tftp**

| 维度 | 说明 |
|------|------|
| 异步文件 I/O | ✅ 原生支持，网络与磁盘并行 |
| 缓存扩展 | ✅ 通过 Handler trait 可实现预读/写入缓存 |
| 窗口扩展 | ✅ RFC 7440 支持，提升吞吐量 |
| 功能 | 完整 TFTP 服务端 + 客户端 |
| 实现 | 纯 Rust，Apache-2.0 / MIT 双许可 |

### 5.3 核心依赖原则

- **优先内置**：使用语言/框架内置功能
- **轻量优先**：选择无重依赖的库
- **成熟优先**：选择社区活跃、文档完善的库
- **避免过度封装**：需求简单则自实现

## 9. 总结

### 方案对比

| 方案 | 体积 | 内存 | 启动 | Linux 单文件 | 开发效率 | 推荐场景 |
|------|------|------|------|-------------|---------|---------|
| **Rust FLTK** | 最优 | 最优 | 最优 | ✅ 无依赖 | 中 | 极致体积/中文输入 |
| **Rust Slint** | 优 | 优 | 优 | ✅ 无依赖 | 中 | 综合最优 |
| Go + Fyne | 中 | 良 | 良 | ✅ 无依赖 | 高 | 开发效率优先 |
| Rust Tauri | 小/大 | 中 | 优 | ❌ 需依赖 | 高 | Web 技术栈 |
| Go Wails | 小/不支持 | 中 | 良 | ❌ 需依赖 | 高 | Web 技术栈 |
| Electron | 差 | 差 | 中 | ⚠️ 体积大 | 最高 | 生态成熟 |
| .NET Avalonia | 差 | 差 | 中 | ✅ 自包含 | 最高 | 迁移成本优先 |

### WebView 方案评估结论

| 指标 | Tauri | Wails | Electron |
|------|-------|-------|----------|
| Linux 单文件可行性 | ⚠️ 需权衡 | ❌ 不支持 | ✅ 但体积大 |
| 依赖系统 WebView | 3-10 MB | 8-15 MB | N/A |
| 内嵌 WebView | 80-100 MB | 不支持 | 120-150 MB |
| 发行版兼容性 | 差（依赖版本碎片化） | 差 | 优 |
| 符合项目目标 | ❌ | ❌ | ❌ |

**结论：WebView 技术方案无法同时满足"单文件、无依赖、小体积"三要素，不适合本项目。**

### 决策建议

| 场景 | 推荐方案 | 理由 |
